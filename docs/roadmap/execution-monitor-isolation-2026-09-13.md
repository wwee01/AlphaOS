# Execution monitor isolation — deployment contract

The scheduler previously ran scan, monitor and research jobs sequentially. A slow scan could delay protection monitoring, and a successful research job could make the general heartbeat healthy while the monitor was fused. This repair assigns monitoring a separate launchd process and reports its own readiness.

## Roles and behavior

- `python -m alphaos.scheduler.worker --role monitor`: only the existing monitor job, with its existing fifteen-minute cadence. launchd invokes it every five minutes. No new AI calls or faster broker polling cadence.
- `--role research`: the existing non-monitor jobs. A scan is blocked unless monitor readiness is established. The integrating `_execute_checked` change must also re-read readiness immediately before every real-paper submission, including manual approval, under monitor ownership. This catches a monitor failure during a slow scan; manual approval does not bypass the halt policy. Outcome collection and other research jobs remain available. Existing scan windows and source/call caps are unchanged.
- `--role health`: a separate five-minute monitor heartbeat. Opens SQLite read-only, constructs no broker, and alerts on initial unhealthy state or meaningful escalation. Private adjacent notification metadata is the only state it writes. A recent research completion cannot substitute for a monitor completion. Monitoring is expected around the clock under the existing cadence, including weekends.
- `--role readiness`: the same read-only check without alert delivery; additionally requires a completed dedicated-monitor worker pass and no in-flight monitor. This is the migration's startup gate.
- `--role preflight`: read-only migration check. Refuses any unfinished scheduler job or unfinished manual monitor pass. It never reaps or modifies those rows.

Normal reconciliation that finds an unresolved cancellation, working close, broker-read uncertainty, or protection incident remains a **completed pass with incidents**. Readiness is false and new scheduled scans are blocked, while monitoring continues. Raised worker failures still create failed job rows and eventually trip the existing fuse. An explicit process failure is not recast as a healthy domain incident.

The heartbeat rejects recent failures/fuses, missing or invalid/future completion times, stale in-flight rows, multiple in-flight rows, recorded execution errors and unresolved protection incidents. Its freshness allowance is the smaller of the existing general heartbeat threshold and the larger of two monitor intervals or one interval plus two launch ticks (30 minutes with present defaults). A fresh in-flight pass can retain worker health, but entry readiness is false until it finishes.

## Ownership and recovery

The canonical ledger path determines a persistent `.monitor.lock` file. A nonblocking OS advisory lock is held throughout the monitor worker and across `JobRunner.run_job('monitor')` and `Orchestrator.run_monitor_once()`. It is reentrant only in the same owning thread. Different threads/processes cannot overlap, even across cadence interval keys. Never delete these files while workers may exist: replacing a lock inode can create two independent owners. The existing SQLite interval key remains the completed-run deduplication backstop.

Research has a separate process lock, so slow research cannot own the monitor's worker slot. Research reaping never touches monitor rows. Scheduled monitor runs leave interrupted `started` rows intact and report that review is required. An explicit manual `scheduler_run_job monitor` can recover a stale monitor row only while holding exclusive ownership, and only a successfully completed pass changes the existing failure streak. Neither deployment nor health clears a fuse, suspension marker, or protection incident.

This is process isolation, not independent infrastructure: both workers still share the Mac, broker access and SQLite. A long database write transaction, machine sleep, lost connectivity or broker outage can still impair both. Those failures must remain visible as unhealthy monitoring. Production broker behavior and launchd activation require the integrating operator's runtime verification.

## Reviewed migration procedure

No service is installed by importing this code or running tests.

1. Integrate the reviewed code and tests into the production checkout. Confirm the intended paper configuration and existing safeguards. Record the reviewed full commit SHA and the SHA-256 digest of the approved `.env` without displaying its contents. The static plists name the production checkout/runtime; activation and resume refuse another checkout.
2. Run `deploy/install_monitor_isolation.sh --stage`. This validates/copies three plists to a staging directory and changes no services. Review the scheduler=research, monitor=monitor and heartbeat=health role arguments.
3. After authorization, run `deploy/install_monitor_isolation.sh --activate --expected-head "$REVIEWED_SHA" --expected-env-sha256 "$REVIEWED_ENV_SHA256"`. These values must come from the reviewed deployment evidence. The installer checks exact HEAD, tracked cleanliness and environment digest before service changes, again before replacement, and before starting research. It first checks for active workers and unfinished ledger work without changing services. It preserves timestamped original operator plists, SHA-256 hashes and enabled-state flags in a private backup directory. It then disables future scheduler/monitor launches and repeats the checks. A refusal before service replacement restores the previous enabled states; no active worker is killed.
4. Once quiet and preflight-clean, the installer replaces the service definitions and loads the independent heartbeat before the dedicated monitor. It verifies their actual registered program, working directory and role arguments, in addition to checking installed files. It loads research only after dedicated readiness passes. A failure after replacement disables research and attempts independent heartbeat/monitor recovery only when each service is absent. An existing unverified service is reported without killing it or creating a duplicate; an old or ambiguous combined scheduler prevents independent recovery. The report distinguishes `loaded_verified` from `UNAVAILABLE`; registration alone does not mean monitoring is healthy. No reset or automatic orphan recovery occurs.
5. With a recent legacy monitor completion, existing cadence may make the first dedicated invocation legitimately not due. The bounded 30-second readiness wait then ends with monitor and heartbeat installed but research stopped. Allow the existing cadence to produce a dedicated pass, inspect its result, then run `deploy/install_monitor_isolation.sh --resume --expected-head "$REVIEWED_SHA" --expected-env-sha256 "$REVIEWED_ENV_SHA256"`. Resume validates the same identities and installed definitions, requires research to be absent, recovers absent independent services if needed, and starts research only after readiness. It never unloads an existing monitor or forces a new broker pass. If readiness remains false, research stays disabled.
6. Verify one completed dedicated monitor row (`worker_role=monitor` in result metadata), normal subsequent cadence, no unresolved incidents, health exit status zero, and no monitor entries from the research worker. Observe a real research scan while monitoring remains independently scheduled.

`deploy/install_launchagent.sh scheduler --expected-head "$REVIEWED_SHA" --expected-env-sha256 "$REVIEWED_ENV_SHA256"` uses this coordinated migration; `all` accepts the same arguments and additionally installs the existing backup job. `deploy/uninstall_launchagent.sh all` stops scheduler, monitor and heartbeat while retaining backup behavior. Stopping only `scheduler` leaves protection monitoring available. After a failed research bootstrap, a registered research service may remain disabled; inspect it and quiesce it before using activation again. Resume deliberately refuses a registered research service, avoiding an implicit stop of a possibly active worker.

Rollback must first quiesce both scheduler and monitor processes. Do not restore an old sequential scheduler while leaving a separate monitor active, because old already-loaded Python code cannot honor the new ownership contract. Preserve the ledger and protective broker orders; inspect any interrupted pass before returning to service.

They cover a blocked research process while monitoring completes, competing monitor processes with different interval keys, thread ownership/reentrancy, historical fuse masking, weekend heartbeat expectations, four repeated domain incidents without disabling recovery, explicit-only orphan recovery, and read-only health/startup checks.

Source/call caps, trading risk limits, strategy selection and monitor interval are unchanged. This patch is not authorization to start services or clear existing incidents. The integrating final-entry check applies the approved unhealthy-monitor halt to manual as well as scheduled real-paper entries.

## Heartbeat notification transitions

Both the dedicated health worker and legacy `JobRunner.heartbeat_check()` use a shared notification helper. It stores `LEDGER_PATH.monitor-notifications.json` and a separate `.lock` beside the ledger, with owner-only permissions. A file lock covers notification decisions and delivery; atomic replacement commits metadata. SQLite remains read-only and unchanged. `readiness` and `preflight` do not invoke notification delivery or create this metadata.

A new unhealthy episode notifies once. Escalation, a newly tripped fuse, or a new protection issue can notify again. Protection identity uses position and status, not per-pass audit row IDs. Increasing age strings, new job timestamps and repeated unresolved-order observations do not repeat the page. Healthy recovery resets the episode without a recovery page. An unsuccessful or interrupted send remains pending and retries on a later health check.

Malformed metadata is reported as `invalid_notification_state_reset`; only this operational sidecar is rebuilt, and prior delivery is never assumed. Unreadable/unwritable metadata is returned explicitly as a notification state error, without claiming delivery. No alert is sent before a pending delivery record can be saved. A crash after external delivery but before the final save can cause a retry: notification delivery and a local file cannot be committed as one transaction. This favors a possible duplicate on that narrow crash boundary over silently losing an alert.
