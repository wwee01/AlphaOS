# Entry contention and approval preservation (N2)

Claude's verification of round two found that a valid proposal reaching entry submission during a roughly four-second monitor pass was permanently marked `blocked`. The result text said deferred, but both manual and automatic callers treated it as terminal; the approval receipt had already consumed automatic capacity.

The entry path keeps the existing entry-submission → monitor ownership order. If the monitor is busy, an entry waits up to ten seconds using a monotonic clock, without holding a SQLite write transaction. Scheduled and manual monitor invocations retain their nonblocking behavior. After waiting successfully, the entry fetches a new market snapshot, checks freshness and price drift, reads current account risk, and checks proposal TTL, persisted approval eligibility and dedicated monitor readiness before submitting. The extra market read occurs only on the contended path. It changes no source subscription, paid AI usage, limits or order placement mechanics.

If monitor ownership is still unavailable at the deadline, `OrderResult.deferred=True`, `blocked=False`, and `state=None` explicitly mean no broker attempt occurred. Contention for the entry-submission lock has a separate typed `EntrySubmissionBusy` exception and produces the same retryable outcome. Other unverifiable account/broker errors still block. A proposal that expired while waiting becomes `expired`; a concurrent rejection or supersession stays intact.

Approval recording is delayed until ownership and final execution guards pass. Automatic eligibility is previewed without recording a receipt; the normal approval engine then rechecks the shared and unattended caps under entry ownership before recording. Manual approval is recorded at the same final point. A timeout leaves no approval receipt, order or consumed approval capacity. Once a submission attempt begins, its approval remains recorded even if the broker rejects it or its response is uncertain; this repair never rolls back that history or retries an ambiguous broker submission.

All execution callers were checked:

- `_handle_proposal` handles deferral before blocked/submitted outcomes, keeps the existing pending status, records `entry_deferred`, increments the pending queue count, and includes the reason in scan notes.
- `approve_proposal` returns `ok=False` with an explicit deferred/pending message. Retrying invokes all existing manual approval checks again, including explicit margin approval. Releasing the lock does not grant standing manual consent.
- CLI `approve`, the console approve API and both dashboard approval buttons use that same `(ok, message)` result. The pending proposal remains actionable; the console still requires a fresh authorized request/nonce.
- Existing durable entry intents are observed before any new approval callback, so repeat observation consumes no second approval and performs no automatic resubmission.

This is bounded waiting with the existing pending queue, not a new autonomous retry scheduler. If the ten-second wait ends, an operator may retry the pending proposal while its original TTL remains valid; subsequent scans retain their existing new-proposal/supersession behavior. No historical proposals or approvals are rewritten, and no migration or production service change is required by the code itself.

Validation includes real thread contention lasting four seconds, manual and automatic/unattended timeout handling, refreshed market/risk/monitor checks, expiry and rejection during waiting, explicit manual margin retry, cap changes during waiting, competing entry ownership, and retained approval consumption after rejected or uncertain submission outcomes. All tests use temporary ledgers and broker-free placement doubles or the existing simulator. Final test counts are recorded with the repair commit handoff.
