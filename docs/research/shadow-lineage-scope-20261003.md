# Shadow scan lineage capture — 3 October 2026

This bounded increment removes repeated environment-lineage work from the time between a shadow source receipt and later symbol assessments. It preserves the configured IEX provider, requested symbols and ordering, 100-symbol request chunks, API count, actual assessment clocks, source timestamps, freshness limits, candidate calculations and shadow safeguards.

Before the change, every candidate or rejection rebuilt lineage with three Git subprocesses plus configuration hashing and a lineage lookup. An offline actual-scanner run at 25235e2 produced 500 fresh candidates using five fake response bodies, 1,500 real local Git subprocesses, 10.487 seconds inside Git, and a 12.012-second scan. Capturing only Git identity once in a scratch counterfactual reduced this to three Git subprocesses and a 1.261-second scan, with equal stable candidate and lineage projections. Both runs retained the full 500-symbol denominator and unchanged source-age gates. In a deliberately near-expiry synthetic fixture, 416 observations expired locally in the original path and zero in the counterfactual. These are local timing measurements and a causal fixture, not production forecasts or a natural coverage gain.

The actual change captures the existing best-effort lineage ID once per shadow scan, after membership validation and universe persistence, before the first data request. A frozen local value is passed explicitly to candidate and rejection writers. An unavailable ID stays None throughout that scan; there is no per-row retry or borrowing from a preceding scan. The next scan calls the existing builder again. Core scans and direct/default helper callers retain their existing per-row behavior. No global, thread-local or scanner-instance cache is introduced.

Each existing chunk diagnostic includes a `lineage_capture` object with version `shadow_scan_lineage_v1`, scope `single_shadow_scan`, lineage ID, recorded/unavailable status, and actual capture start and completion times. A recorded ID means the existing builder returned an identity; it does not authenticate every identity component or prove that repository files stayed unchanged afterward. The three Git reads inside the existing builder are not an atomic filesystem attestation. The chunk's unchanged `shadow_chunk_assessment_v1` observations still carry their separate actual assessment clocks and source/receipt provenance. A scan may now record one lineage snapshot even when no row becomes a candidate; it remains measurement metadata.

The prior September 28 saved opening cohort had 107 stale-on-arrival observations and four additional local expiries. This change targets avoidable processing cost only. It cannot make an already-old quote or minute bar fresh, restore absent source events, change asset eligibility, or satisfy the separate trailing coverage/latch/canary requirements. No feed/universe/threshold changes, latch reset, activation, historical rewrite or extra retrieval is included. A separate offline malformed-payload observation is outside this increment.

Verification preserves the failing before cases, checks actual scanner candidate/rejection paths, current-time expiry, delayed capture, missing lineage, next-scan identity/configuration changes, failed-scan isolation, unchanged core behavior and request ceilings. The diagnosis artifacts under the parent evidence directory retain input/source hashes and the synthetic timings. The initial diagnostic fixture's equality assertion failed because relative-volume calculation intentionally depends on receipt time; the retained second fixture uses absent prior volume and a positive 3% momentum signal, so its equality comparison does not suppress real receipt-time semantics.
